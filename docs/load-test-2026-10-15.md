# Music Challenge 正式站壓力測試

測試時間：2026-10-15 02:04–02:11（台灣）。目標：`https://music-challenge.zeabur.app`，Tencent Jakarta 指定伺服器，2 vCPU、可用記憶體 3,724 MB。部署版本為 PR #4 合併後的 `58d354e3d6b93cf88502f6d70221ed0613c68479`。

## 結論

- **已驗證 816 條同時 SSE 連線**，相當於 16 個房間、800 位玩家加 16 位主持人。最高階觀察 20 秒，零斷線、健康檢查 p95 81 ms。這是實測下限，沒有測到連線硬上限，也不是長時間穩定性保證。
- **已驗證 102 條連線下，每秒 20 次混合請求**，持續 30 秒，600 次請求全部成功，p95 107 ms。此流量為 60% 錯誤答案提交、20% 曲庫讀取、20% 排行榜讀取。
- **大量全員同步已有可見延遲**：兩個滿員房間同時更新時，三次波次的全員送達 p95 為 1,383 / 1,882 / 1,990 ms。觸及預設 1,500 ms 門檻後停止加壓。每次有完整流量量測的波次約 9.98 MB。
- 不能把「816 條保持連線」說成「816 人同時搶答仍流暢」。本次只驗證到 100 位玩家加兩位主持人的上述混合操作負載；密集搶答型活動應先保守以單個 50 人派對規劃，再改善同步效率並重測。

## 資源與限制

測試前整台伺服器 CPU 約 5.3%、記憶體約 48.6%。測試期間取得的 CPU 樣本最高約 44.8%；含測後樣本的記憶體最高約 65.5%。這是 Zeabur 回傳的整機離散樣本，包含其他服務；不是連續峰值，也不是 Music Challenge 單一容器的 CPU 分析。尚不能據此排除 Node.js 單執行緒、磁碟或短暫網路瓶頸。

廣播複測時，本機產生負載的程式 CPU 約單核心的 14.6–17.6%，事件迴圈 p99 約 32–34 ms，未見本機 CPU 滿載。所有流量來自一台電腦、同一條外網路徑，無法分離伺服器出口頻寬、網際網路與測試端下載頻寬的影響。音樂由 Apple CDN 提供，本次未下載音源；也沒有跑手機畫面渲染、真實音訊播放、好友對戰獨立負載或數小時穩定性測試。

從原始碼可見，派對每次操作會讀寫含題庫／牌組的完整房間 JSON；全員廣播對每位收件者重新產生排名與狀態，再序列化完整玩家列表。這些是後續量測及優化的具體候選，**本次未以伺服器 profiler 證實各項耗時比例**。優先量測並縮小廣播資料、減少重複運算與完整狀態寫入，再重跑相同負載；目前資料不足以判定升級記憶體可以解決延遲。

三輪測試共建立 20 個房間、1,020 個測試身分。所有房間已確認 `finished`，測試 SSE 全部關閉；未建立分享成績或提交排行榜分數。已結束房間與測試身分保留在資料庫，未刪除正式資料。

測後首頁、`/healthz`、`/api/health`、曲庫與排行榜皆 HTTP 200；10 次健康檢查全數成功，暖連線約 74–77 ms，首次 355 ms。前端部署 RUNNING，後端部署仍為原版本；取得的後端日誌無新增錯誤，前端最新 100 筆日誌未見 5xx／error。此日誌抽樣不是完整流量稽核。
